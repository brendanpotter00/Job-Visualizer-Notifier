# Environments: prod vs dev (READ THIS FIRST)

This repo is checked out **twice** on the laptop. One copy is **production** — a launchd
worker enriches real JVN jobs from it every 10 minutes against the authoritative database.
The other is **dev** — where humans and agents make changes. Editing the wrong tree pushes
untested code (or a half-saved file) into production within one tick.

## The two checkouts

| | **PROD** | **DEV** |
|---|---|---|
| Path | `~/developer/personal/app` | `~/developer/personal/job-enricher` |
| Role marker (`.checkout-role`) | `prod` | `dev` |
| launchd worker | **runs here** every 600s | never |
| `data/enricher.db` | **authoritative** (real jobs) | throwaway |
| `.env.local` → `JVN_BASE_URL` | real JVN (Railway) | local/staging JVN, or absent |
| Who touches it | only `scripts/deploy.sh` | you + agents (freely) |

> The `app` checkout root is the production home; `job-enricher` (the original,
> naturally-typed path) is intentionally the dev workspace so muscle memory lands you
> somewhere safe.

## How to tell which one you're in

`CLAUDE.md` is git-tracked, so it is **byte-identical in both checkouts** and can't itself
say "this is prod." The per-directory truth is an **untracked, gitignored** marker file:

```bash
cat .checkout-role      # -> "prod" or "dev"  (missing => assume dev, but verify your path)
```

- `prod` → **stop.** Do not edit files or run ticks by hand here. Make the change in dev,
  open a PR, merge, then `scripts/deploy.sh`.
- `dev` → safe to edit and experiment.

**Agents:** always work in the dev checkout, or in a git worktree of it
(`.claude/worktrees/…`). Never edit prod. The background-job harness already isolates edits
into worktrees; this just tells you which repo to start from.

## State ownership

`git clone` copies only tracked files. Everything below that is authoritative in prod is
**gitignored/untracked** and must be preserved separately — it does NOT travel with git.

| State | Where | Authoritative? |
|---|---|---|
| `data/enricher.db` (~18 MB) | prod only, gitignored | **YES** — the production datastore (jobs, enrichments, ticks, knobs `meta`) |
| `.env.local` | per-checkout, gitignored | **YES** — carries the JVN URL + `INTERNAL_API_KEY` |
| `data/.tick.lock`, `data/chunks/` (the pipeline's `classify-*.json` / `judge-*.json` scratch) | prod, local | no — per-tick scratch, regenerated |
| `golden/seed/golden.json` + `golden/scorecards/baseline.json` | git-tracked | travels via git (dev has it too) |
| `golden/scorecards/predictions*.json` | gitignored | no — regenerated by `/enrich-eval` |
| `.venv/` | gitignored | no — rebuild with `uv sync` |

All durable paths resolve **package-relative** (`REPO_ROOT = Path(__file__).resolve().parents[2]`
in `src/job_enricher/store.py`), so each checkout automatically reads/writes its **own**
`data/`, `golden/`, and lock — the two can never collide. The only cwd-sensitive piece is
`.env.local` (loaded relative to the process working dir, `config.py`), which the launchd
plist's `WorkingDirectory` and the wrapper's `cd` already pin to the prod root.

## Dev-safety (do not skip)

Because state is per-checkout, a stray `cli pull` / `/enrich-tick` in **dev** would claim and
write back **real production jobs to real JVN**. Keep dev harmless:

- Dev `.env.local` → `JVN_BASE_URL=http://localhost:8080` (local JVN), **or leave it absent**:
  the base URL harmlessly defaults to `http://localhost:8080` (`config.py`), and the CLI hard-fails
  on the missing `INTERNAL_API_KEY` — the JVN client raises `RuntimeError` before any request
  (`jvn_client.py`), so nothing reaches real JVN (safe by default).
- Dev's DB is a fresh `cli init` (evals still work — the golden seed is in git). You may
  optionally seed dev with a *copy* of prod's DB for realistic testing; the env guard above
  keeps write-back off real JVN.

## Deploy (dev → prod)

Develop in dev on a branch → PR → merge to `main` → deploy pulls `main` into prod. The deploy
is a controlled swap between ticks (`scripts/deploy.sh`, run **from the prod checkout**):

```bash
cd ~/developer/personal/app
scripts/deploy.sh            # fast-forward the current branch (main)
scripts/deploy.sh v1.2.0     # or check out an exact tag/branch/sha
```

The script: refuses unless `.checkout-role == prod`; pauses the launchd worker
(`launchctl unload`); aborts if a tick is mid-flight or the tree has uncommitted tracked
changes; `git fetch` + fast-forward/checkout; `uv sync`; reloads the worker; runs
`cli health`. The single-flight lock is a second guard — a tick that starts during a checkout
exits 75 ("lock held") rather than reading a half-updated tree.

> ⚠ **Schema migrations run inside step 6's `cli health`, with the worker PARKED.**
> `cli health` opens the DB, which runs `init_schema()`, which runs the migration
> ladder. A long migration there is a parked-worker outage, not a slow command.
> **Rehearse it first** (`scripts/rehearse_v4_migration.sh` — on a
> `sqlite3 ".backup"` copy, never `cp`, because the DB is WAL-mode) and **split
> the migration if it takes more than 30 s.** See
> `docs/RUNBOOK-subcategory-backfill.md` §4.
>
> ⚠ **`init_schema` has no downgrade and `user_version` only moves forward**, so
> the `.backup` copy IS the rollback artifact for a schema change. A `git`
> rollback alone does NOT undo a migration.

> **Deploying a changed default does NOT change a running knob.** Runtime knobs live in
> prod's `meta` table (not git). An explicit knob (e.g. `classify:engine`, `classify:model`)
> overrides the committed code default forever, so merging a new `*_DEFAULT` and deploying
> leaves prod on the old value. The deploy's `cli health` prints the live `classify_engine`/
> `judge_engine`/`opencode_model` alongside `classify_model`/`judge_model` so you can see what
> prod actually runs — the **engine** is authoritative; the Claude-tier model fields are inert
> unless the matching engine is `claude-code`. To make prod follow the newly-deployed default,
> `cli reset-knob <meta:key>` clears the override (or `set-<knob>` sets it explicitly).

**Rollback:**
```bash
cd ~/developer/personal/app
scripts/deploy.sh <previous-tag-or-sha>
```

## How prod runs

- **launchd agent** `~/Library/LaunchAgents/com.bp.job-enricher.plist` — `StartInterval=600`,
  `WorkingDirectory` + `ProgramArguments` point at the prod checkout; regenerate it by running
  `scripts/install_launchagents.sh` **from the prod checkout** (it derives the path from its
  own location — no hardcoded path).
- **Wrapper** `scripts/enrich_tick_wrapper.sh` — acquires the lock, pre-runs `pull`+`clean`,
  then hands off to `claude -p /enrich-tick-once`; pushes metrics after. It anchors to its own
  checkout via `PROJECT_DIR="$(cd "$(dirname "$0")/.." && pwd)"`.
- **Logs** — `~/Library/Logs/job-enricher.log` and `.err`.

```bash
launchctl list | grep job-enricher          # is the worker loaded?
tail -f ~/Library/Logs/job-enricher.log     # watch ticks
cd ~/developer/personal/app && uv run python -m job_enricher.cli health
```

## Dashboard (dev-only, not deployed)

The local dashboard (`dashboard/` SPA + `src/job_enricher/dashboard.py`) is a **dev tool**,
not part of the prod deploy surface — `scripts/deploy.sh` never touches it. Launch it with
`scripts/run_dashboard.sh` from the dev checkout: it updates to the latest `main`, rebuilds
`dashboard/dist` (gitignored — never travels via git or deploy), and serves on
`127.0.0.1:8788`. `cli dashboard` refuses to serve from a `.claude/worktrees/` path, so a
stale scratch worktree can't quietly keep serving an old build. Never run it from the prod
checkout, and never place it behind the Cloudflare tunnel.

## First-time prod setup (how `app/` was created)

Recorded so prod can be rebuilt. Run with the worker paused; keep the source DB intact until
prod is verified so rollback is just re-pointing launchd back.

1. `launchctl unload ~/Library/LaunchAgents/com.bp.job-enricher.plist` (confirm no tick running).
2. `git clone https://github.com/brendanpotter00/job-enricher.git ~/developer/personal/app`
   then check out the production commit; `cd ~/developer/personal/app && uv sync`.
3. Copy authoritative state into prod: `data/enricher.db` (+ loose `data/` files) and
   `.env.local` from the old checkout → `app/`. Write `echo prod > app/.checkout-role`.
4. `cd ~/developer/personal/app && scripts/install_launchagents.sh` (regenerates the plist
   pointing at `app`), which loads the worker.
5. Verify prod green (below). Only then convert `~/developer/personal/job-enricher` to dev:
   reset its `data/` to a fresh `cli init`, point `.env.local` at local/staging (or remove it),
   `echo dev > .checkout-role`, and `git worktree prune`.

## Verification

- **Prod:** `cd ~/developer/personal/app && uv run python -m job_enricher.cli health` (job
  counts match pre-migration); `cat .checkout-role` = `prod`; watch one interval of
  `~/Library/Logs/job-enricher.log` for a clean tick + `metrics-push`.
- **Dev:** `cd ~/developer/personal/job-enricher`; `cat .checkout-role` = `dev`;
  `uv run pytest` passes; a `cli pull` does **not** reach real JVN.

## The SWE subcategory backfill

Both lanes — `subcategory-backfill` (label) and `subcategory-push` (drain) — are
**hand-launched from the PROD checkout**, not from launchd and not from the tick
wrapper. Each takes its own lock (`data/.backfill.lock`,
`data/.subcategory-push.lock`) so neither can collide with the live tick's
`.tick.lock`.

⚠ **The procedure is `docs/BACKFILL.md`. Read §1.1 first** — running from the dev
checkout against the prod DB is the specific mistake that page exists to prevent.
