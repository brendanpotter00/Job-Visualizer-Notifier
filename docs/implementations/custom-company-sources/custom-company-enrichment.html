How to settle it with a measurement instead of an opinion

You have a natural experiment sitting in prod: 16,693 jobs that already have both a description and a description-backed label.

  1. Take a stratified sample of ~300 of them (across source and category).
  2. Re-run the classifier on title only, description withheld.
  3. Compute label agreement vs the description-backed label — separately for category and level, and separately per category (I'd expect level to hold up and category to be where it breaks: "Analyst", "Engineer II", "Specialist").

That agreement rate is the number that decides D3 — and whether title-only labels should be published to the UI at all. Cost: one offline batch, judge disabled. Nothing else in this plan should be trusted over it.

§07.3 — The captured endpoint as identity — evaluated honestly

This is the strongest signal available, and you already collect it and already prove it. Your Spotify row's provider_config.discovery.network.requests[] holds 14 recorded URLs, exactly one marked "state": "chosen":

{"url": "https://api.lifeatspotify.com/wp-json/animal/v1/job/search",

✔ Why it beats the entry URL

  • It is what the board is, not what a marketing page happens to link. /jobs, /jobs?l=london and / all capture the same feed — three entry URLs, one endpoint.
  • It is proven, not guessed: discovery only marks it chosen after replaying it from our own servers and counting records.
  • It survives a front-end host move or a site redesign as long as the feed is unchanged.
  • It is already persisted. No new capture, no new browser time.

✕ Where it still fails — say this out loud

  • It does not solve Spotify. Lever's feed and lifeatspotify's feed are two different, both-real endpoints. Endpoint identity is exactly as blind here as URL identity.
  • Two tenants behind one multi-tenant feed host collide on origin+path; the tenant is in a query param, and which param is tenant-bearing is not derivable.
  • An API version bump (/v1/ → /v2/) reads as a brand-new board.
  • Only discovered boards have one. ATS-resolved boards (workday:cisco) have none — they use ats:token, which is better anyway.
Verdict: use it as the P1 key, not as a merge oracle. Store the chosen endpoint's origin + path as a second, nullable identity column and match on it in addition to canonical_source_key. That makes "two users paste two spellings of one careers site" work reliably, which is the case P1 is actually about. It does not make "two users paste two different boards of one company" work, and I could not find anything cheap that does — see §07.6 for the only approach I'd trust, which is a suggestion rather than a merge.

§07.5 — The consequences that make this hard

Privacy

A must not learn B exists — and one field currently leaks

The ownership model already holds up: the list endpoint joins user_companies, and its absence means "not yours" (db_models.py:717-724). Sharing does not change that — B's row simply appears in B's list, A's list is untouched, and neither can enumerate the other.

What becomes a shared fact: open_job_count, health_state, last_success_at, tracking_started_at. So B adds Jane Street and immediately sees "tracked since 2026-08-21, 235 jobs". B learns somebody tracked it, not who. I judge that acceptable — it is the feature you asked for — but it should be a stated decision, not a surprise.

What must not leak, and would today: provider_config.discovery is returned to the owner and contains the first user's Browserbase live_view_url, their full 14-entry captured request log, and a raw job sample. Under sharing that blob would go to every owner. Also never expose: the owner list, and company_add_attempts (it carries user_id + the raw submitted URL). Fix the provider_config projection before sharing ships.

Deletion

Less broken than it looks — the guard is already there

I expected this to be the blocking conflict. It isn't. remove_owned_company already counts remaining owners and returns 'unlinked' without purging when any remain (custom_companies_service.py:936-943), and its own docstring says the count is "the guard that makes this still safe if row sharing is ever introduced". A removing while B remains is already correct today. Whoever wrote commit 7a5a57b left the door open on purpose.

Two things are still unsolved:

  • The last owner still purges everything. If B leaves after A, 55 days of history dies — and the next person to add Spotify pays for a fresh scraper and starts at zero. Under sharing, history is a shared asset and hard-delete stops being the obvious default. That is D5.
  • "Remove" changes meaning. Today it means delete. Under sharing it means stop showing me this for everyone but the last owner. The confirm-dialog copy has to change or it lies to the user.
History

Yes, B inherits it — and it costs nothing

Confirmed, and here is the exact reason. Jobs are keyed (source_id, id) and source_id = custom:<company_id>. One company row is one namespace is one history. B joining an existing row sees every row already in it, first_seen_at and all — no backfill, no copy, no migration.

first_seen_at is when A's scraper first saw the job, not when B joined. That is the right number for a hiring-trend chart and the wrong number for "new since I started watching". The trend page already draws that distinction with tracking_started_at (stamped on the first VERIFIED harvest, fetch_custom_company.py:406) shading the pre-tracking bucket — B inherits A's, which is correct.

The never-wrong-close guarantees are untouched, and this is the property that makes option 1 safe: closes are decided by the harvest gate and job_freshness, both scoped per source_id, and there is still exactly one scraper writing each source_id. Sharing adds owners, never writers. Option 2 (fan-out) would add writers — that is the real reason to prefer 1.

Link to the hiring-trend page. Don't scrape it again.

Where it goes: routers/user_companies.py, right after discover_ats returns a candidate and before the ATS add path runs. One lookup: SELECT id, display_name FROM companies WHERE visibility='public' AND ats=%s AND board_token=%s.

Why I did not turn enrichment_claim_without_description on locally, even though you asked. It would change nothing you could observe. The flag gates /pending, and /pending is only reached when an enricher calls it — your enricher points at prod, not at jobscraper_pr243. If you disagree, the disagreement is worth having: the one real reason to set it locally is to make the local API's behaviour match prod so a test written against local doesn't pass for the wrong reason. I judged the confusion cost higher than the parity benefit, because a local flag that looks meaningful but is inert is exactly the kind of thing that misleads the next debugging session.
