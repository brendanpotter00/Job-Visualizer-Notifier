Calls, settings and why

  1. Monitor events. Three narrow event_stream Monitors (seed, Series A+, AI launches), base, daily, include_backfill, a 9-field output schema. The loop polls GET events once a day (no webhook: the loop runs on a laptop with no public URL).
  2. Domain lookup. For events with no website: one Search call (advanced, the default and best-ranked mode; the lookup is not latency-sensitive); keep the top result whose host carries the company name and is not a news/directory/social site.
  3. Dedupe against every card ever posted (free; before any spend).
  4. In parallel: FindAll preview for founders/C-level/VPs of that exact domain (then an is_person filter); the core brief Task; the pro team-tally Task.
  5. Founders fallback: if FindAll keeps nobody, use the brief's founders.
  6. Pedigree: a Task Group, one base run per leader.
  7. Free ATS check (Greenhouse/Ashby/Lever public APIs), deterministic scoring, POST the card.

Scoring (deterministic, in code — no model)

Talent (0–100) is a 50/50 blend: leaders (0–50) + team (0–50). Both known: the sum. One known: that half doubled (missing data is not a weak team). Neither: null.

Leaders: top school +8 each (cap 24); top-tier employer +10 each (cap 30); prior founder with an exit (acquired/IPO) +15 each (cap 30); 10+ years +5 each (cap 10), weighted by Parallel's field confidence (high ×1.0, medium ×0.8, low ×0.5). That 0–94 is rescaled ×50/94. Founding without an exit scores 0.

Team, from the tally of n profiles. The tally lists schools and employers, not people, so a side's share is its top-list entries over max(n, entries listed). Top schools 25 × min(1, share/0.5); top employers 25 × min(1, share/0.5); each rounded once and summed, so the shown points add up. No prior exits: those are checked on the leaders, not the team (an older card's tally count is ignored). A side with nothing listed is missing, not 0: the other side is scaled to 50. Under 5 profiles the team counts n/5 and the rest follows the leaders' half. Null with no profiles or no background listed. radar.sh rescore recomputes stored cards for $0.

VC (0–100): tier-1 lead 60 / participant 45; tier-2 lead 35 / participant 25; Y Combinator 15; extra investors in a tier add up to a cap; round size bonus +15 (≥$50M), +10 (≥$20M), +5 (≥$10M); named but untiered investors +10.

How to benchmark it properly (recommended)

  1. Gold set. 20–30 companies with hand-verified facts: founders and titles, schools, prior employers, exits, latest round (amount, date, lead), website, ATS board. Mix famous and obscure, US and EU, funding and launch.
  2. Record once, replay forever. Save each Parallel response as a fixture (the loop already writes request/response JSON); score fixtures offline so re-scoring costs $0.
  3. Metrics per field: leader recall and precision (vs gold founders), school/employer/exit accuracy, round amount within 10%, date within 7 days, website exact, ATS exact; plus the share of fields with high confidence that are wrong (calibration).
  4. Processor sweep: run the gold set on base / core / pro per step and plot accuracy vs cost; keep the cheapest setting within ~2 points of the best.
  5. Regression gate: re-run the gold set before changing any setting, prompt or schema (the repo already does this for location parsing in src/backend/api/eval/).
  6. Score sanity: check that the talent/VC ranking matches a human ranking of the gold set (rank correlation), not just field accuracy.

How to know the settings are correct

  • Request shapes are pinned by tests. Every call's parameters (processor, generator, schema rules like additionalProperties: false, match conditions, date window) are asserted against fakes in scripts/tests/unit/test_launch_radar_*.py, and were checked against the installed parallel-web 1.3.5 SDK signatures and the OpenAPI spec in your docs folder.
  • Dry runs print the exact requests and costs before any spend: radar.sh run --dry-run, backfill --dry-run, refresh --dry-run, import --dry-run.
  • The ledger is the audit trail. One row per billed call (step, company, estimate, run). Compare it monthly with the Parallel dashboard usage; a gap means an estimate is wrong or a call billed without a reservation.
  • Monitor health. radar.sh monitors-cancel confirms cancellation; the run log reports events per Monitor each day — a Monitor at 0 events for a week needs a new query.
  • Live smoke test after any change: refresh --domains <one known company> (≈ $0.05) and compare the card with the gold facts.

Gaps and next steps

  1. Decide the production cap model (lifetime vs monthly) and set LAUNCH_RADAR_SPEND_CAP_USD on Railway accordingly.
  2. Build the gold-set eval before tuning anything else; it turns "looks right" into numbers.
  3. Tune the seed and launch Monitor queries (they rarely fire); measure events/day per Monitor for a week.
  4. Reconcile ledger vs invoice after the first production month.
  5. Keep the team tally (38% of per-company cost): it is now Talent's team half; dropping it would leave every card scored on its leaders alone (doubled).
