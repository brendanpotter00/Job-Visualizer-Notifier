00 Read this first

Sixteen agents explored both repos, measured the live corpus, and adversarially reviewed the result. The taxonomy and the UI are solid. The delivery mechanism is not — and the reason is a capacity fact, not a design flaw.

The finding that reshapes the plan

The enricher is already underwater. It classifies 485 jobs/day against 495–552 arrivals/day. The last 100 ticks all hit the 38-row cap; each tick runs ~6,710s and the next starts 62 seconds later, so the GPU is at ~100% duty cycle. 282 rows have been stuck in cleaned since 2026-07-13, and 56,656 listings have never been enriched at all.

There is no spare capacity to put a backfill into. Adding subcategory work to the existing tick doesn't fill idle time — it lengthens every tick, which reduces ticks/day and pushes classification further below the arrival rate. "Backfill without adding latency" cannot be satisfied by scheduling; it needs either a cheaper labeling path or a separate lane. That is Decision 1, and it is the only one that gates the rest.

What is ready to build

  • The rename. One label, three sites, plus a changelog entry. The code comment that blocked it explicitly authorizes this exact change.
  • The taxonomy. 15 subcategories, every size measured against 11,139 real rows.
  • The schema. TEXT[] + dimension table, with a tri-state that makes the backfill resumable.
  • The UI. A nested MUI checkbox tree, verified against the installed MUI 7.3.6 internals.

What must be resolved before code

  • Backfill capacity — no lane exists to run it in.
  • The eval gate cannot fire — 21 human labels against a hard min_n=50.
  • Two data-loss paths — admin corrections silently wipe subcategories.
  • Production runs from a different checkout than the one this plan edits.

Yes — we label from the title first. The description is only the fallback.

You asked whether we can just use the title. We can, and it does most of the work: 6,535 of 11,119 SWE rows (58.8%) resolve from the title alone — "Senior Backend Engineer", "iOS Software Engineer", "Site Reliability Engineer" need nothing else. Those are cheap, high-precision, and need no model call at all.

The description only matters for the other 41.2% (4,584 rows) where the title is generic — 953 of them are literally just "Software Engineer". For those the title genuinely carries no specialty, so something has to read further or the row stays unlabelled.

The reason the empty-description number matters isn't that we prefer descriptions — it's a trap in the backfill query. 2,287 SWE rows (20.6%) have clean_description = '' rather than NULL, deterministically per company (capitalone 606/606, nvidia 439/439, gm 271/271, disney 172/172). A backfill testing IS NOT NULL would believe it had 11,119 descriptions and silently feed the model 2,287 empty strings. Test length(clean_description) > 200 instead. Where a title-only row also has no description, it gets labelled from the title or left [] — never guessed.

Two more measurements that shaped the design

9.0% of SWE jobs name two or more specialties in the title alone (1,005 rows), and 59.1% of the title-generic rows map to 2+ competing tag buckets. A single scalar subcategory column is provably lossy — this is why the field is an array, which you confirmed.

Tags are a strong prior, not a labeler. Where a title independently names a specialty, tags agree 86.2% of the time — but on the title-generic rows only 20.9% resolve to exactly one bucket. Tags can cheapen the backfill; they cannot replace it. (Per your note, they stay a pipeline input — see §09 on hiding company tags from the UI.)

You were right about AI — the data backs you, decisively

You said applied AI engineering is "just software engineering with a flavor of AI" and not ML engineering. Measured against the corpus: the two populations are almost exactly the same size — AI Engineering 530 rows (4.76%), Machine Learning 528 rows (4.74%) — and they barely overlap. Only 32 titles (0.29%) hit both signal sets, and reading all 32, just four are genuine coin-flips. Both clear the dead-checkbox floor by roughly 4.8×. Your own reference board listed "AI Applications" and "ML Engineering" separately too. So the AI bucket becomes two, not one.

The tagger already agrees with you, incidentally — left to itself it produced two distinct tag families: agent-*, rag, ai-evals, agent-orchestration on one side, and mlops, ml-infrastructure, on-device-ml, production-ml on the other.

Quant: yes — but only because the signal is in the employer, not the title

My first instinct was to tell you no. The word test says it's a dead checkbox: only 20 SWE titles (0.18%) contain "quant" or "quantitative", and 46 more quant titles already sit in data_scientist — correctly, since a Quantitative Researcher is a scientist under the existing §1 rules and that doesn't change.

But you already track the firms. DRW (56), IMC (53), Jump Trading (36), HRT (19), Akuna (14), Belvedere (8), CTC (7) are all on the board — and 175 of their software-engineering roles (1.57% of the corpus, 147 OPEN) are trading-systems work. Most just don't say "quant" in the title: a "Software Engineer" at Jump is a low-latency trading engineer. So the bucket is real and clears the floor — the title regex was simply the wrong instrument. 15 subcategories.

Two things I'd own about it. It's the smallest bucket on the list, and it's concentrated in ~7 employers, so if those boards go quiet the checkbox thins out. And like Forward Deployed it's a domain rather than a where-the-code-lives position — which multi-label makes harmless: a trading-systems engineer gets [quantitative, backend] or [quantitative, infrastructure_platform] rather than a false choice. The decision rule must read the description and employer for market/latency/exchange/pricing signals, never the word "quant".

Two corrections the measurement forced — both matter

1. "Inference / serving" moves to the Machine Learning side, not AI Engineering. That single token caused ~90% of the measured overlap: titles like "Senior Deep Learning Software Engineer, Inference — TensorRT" and "Staff ML Engineer, Generative Model Performance & Efficiency" are model-side work that merely names LLMs as the object being optimized. Building an inference stack is ML; calling one is AI Engineering. Fixing this drops the overlap from 0.40% to 0.29%.

2. Never route on the ai tag or on AI mentions in the description. 2,462 SWE rows — 22% of the whole corpus — carry an ai/ml family tag while being ordinary backend and full-stack jobs ("Senior Software Engineer" ×88, "Principal Software Engineer" ×66). 11.5% of plain SWE descriptions mention LLMs. Keying off mentions would drag ~1,243 plain rows into AI Engineering, inflating it to ~16% and hollowing out Backend. The classifier must ask what the engineer ships, never whether AI is mentioned.

The tie-breaker for the case that will actually bite — an engineer building an LLM feature at a company that also trains frontier models: route on what the person in this role changes, not what the company builds. If the responsibilities never include altering a model's weights, its training data, or its serving stack — only calling, prompting, orchestrating or evaluating a model that already exists — it is AI Engineering.

Why nothing here cannibalizes a top-level category

A subcategory is evaluated only after §1 has already returned software_engineering. It partitions an existing set and structurally cannot re-route a job. So "Data Science" stays data_scientist, firmware bring-up stays hardware_engineer, and sales engineering stays business_ops — the §1 rules are untouched. That single structural fact dissolves the entire collision problem.

Deliberate exclusions

  • Engineering Management — level=manager already covers 660 SWE rows. Double-encoding invites disagreement.
  • "General / Other" — 41.2% of titles carry no specialty; a General box would instantly be the biggest option and the model's lazy default. Unlabelled is [], an explicitly correct answer.
  • Solutions Engineering — promises SWE jobs, delivers sales engineering.
  • iOS / Android split — two ~1.5% boxes near the dead floor.
  • Networking — clears the floor at 2.1% but fragments Infrastructure. Decision 2.

3. When does the checkbox UI go live? Decided — flag, flip at 90%

A subcategory filter hides rows with no label, so on day one that's 100% of the corpus. You proposed "feature flag the front end for now and let the backfill run for like a week" — that's exactly right, and with the Claude engine the window shrinks from a week to roughly overnight.

You asked: is the 90% enforced, manual, or read from the database? Fair question — "90%" is hand-waving unless something computes it. Concretely: the number is computed, displayed, and the flip is manual. The admin work in §09 already adds two counters to the health snapshot — swe_open_total and swe_subcategorized, both plain SQL over enrichment_category='software_engineering' AND status='OPEN' — so the admin page shows a real "N of M labelled (X%)" tile you can watch drain. When it crosses, you (or I) flip the flag.

I deliberately did not make it auto-reveal on a computed threshold. Two reasons: a filter that switches itself on mid-session is surprising, and a threshold that hovers near the line would flap the UI on and off as jobs arrive and close. A number you can see plus a switch you throw is more predictable than magic, and it costs nothing extra since the counters are being built anyway.

You asked: can the switch live in the admin dashboard and persist, rather than being an environment variable — then get deleted once it's permanently on? Yes, and it's the better design. I'd assumed an env var; that's the worst of the options because flipping it needs a Vercel redeploy, which makes an instant decision into a deploy event. Worth knowing first: JVN has no feature-flag mechanism today — Feature/FeatureUpvote are the user-facing feature-voting tables, not flags. So this is a small build, and here's the shape I'd propose:

  • One key/value app_settings row plus a GET/PUT on the admin router and a single toggle in the admin page — deliberately mirroring the enricher's existing knobs pattern (_KNOB_SETTERS), which you already use, rather than inventing a second idiom.
  • It sits next to the coverage tile from §09, so the number you're watching and the switch you throw are in the same place. That's the whole ergonomic win over an env var.
  • Delete it in a follow-up PR once it's permanently on — exactly as you said. I'd put the removal in the plan as a named step rather than an intention, because flags that were "temporary" are how flag debt happens. One boolean, one endpoint, one switch, one deletion.
The gotcha that would otherwise bite you

GET /api/jobs/facets is RTK-Query cached for an hour on the client. If the flag is read through the facets response, flipping it does nothing for up to an hour on any open session — you'd flip the switch, see no change, and reasonably conclude it's broken. Two ways out: return the flag from a short-TTL endpoint instead of riding on facets, or invalidate the facets tag on toggle. Either is fine; picking neither is the bug.

The elaboration you asked for, kept below for the record.

The situation. Every software-engineering job gets 0–2 subcategories. Most get at least one, but some come back empty — [] — because neither the title nor the description says what kind of engineering it is. A bare "Software Engineer" at a company whose posting is all mission-and-culture boilerplate genuinely has no specialty signal, and guessing would be worse than admitting it. After backfill I project roughly 747 OPEN software-engineering jobs (~9%) in that state.

The question is what those 747 do when someone ticks "Backend".

If you check "Backend"…Hide unlabelled recommendedShow unlabelled
What comes back~2,000 jobs actually labelled Backend (plus Full Stack, via the OR expansion)Those same ~2,000 plus all 747 unlabelled — about 27% of results are "we don't know what this is"
Check "Mobile" instead~270 mobile jobs~270 mobile jobs plus the same 747 — they'd now be 73% of the page
What the filter means"Jobs we're confident are Backend""Jobs that are Backend, plus everything we couldn't read"
The cost you payA Backend job we failed to label is invisible to someone filtering BackendEvery one of the 15 checkboxes returns the same 747 rows, so the filter stops narrowing — which is the entire point of a filter

Why I recommend hiding. The 747 aren't a random sample — they're the same 747 every time. Showing them means the smaller buckets get swamped: on Mobile they'd outnumber the real results three to one. That doesn't make the filter more complete, it makes it useless in exactly the cases where narrowing matters most. And nothing is ever actually lost: ticking Software Engineering with no children checked still returns all 11,139 rows, unlabelled included — so a browsing seeker sees everything, and only someone who explicitly asked to narrow gets the narrowed set.

The mitigation that makes hiding honest is a visible count in the filter UI — "747 software-engineering jobs aren't sub-classified yet and are excluded" — so it's never a silent hide. That's the difference between my recommendation and today's behavior, where matchesCategory already hides unenriched rows while the tooltip claims they "still appear".
